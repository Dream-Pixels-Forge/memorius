# Backend Analyst Report — memorius

**Target:** `Dev/cli/memorius` — Python memory vault, v0.9.3. Core engine `VaultEngine` (`memorius/vault.py`). Modules: `meta_store`, `vector_store` (+`sqlite_vec_store`), `graph`, `search_module`, `reranker`, `embeddings`, `consolidation`, `temporal`, `learning`, `session`, `factcheck`, `context_inject`, `obsidian`, `store_module`, `backup`, `doctor`, `single_instance`, `config`, `models`, `validation`, `hooks/engine` + adapters. Servers: `mcp_server.py` (stdio JSON-RPC), `rest_server.py` (FastAPI). CLI: `memorius/cli/main.py`.

## Scope & Entry Points

- **VaultEngine** (`memorius/vault.py:34`) — high-level orchestrator combining ChromaDB/sqlite-vec vector store + SQLite metadata store. Hierarchy: Vault > Shelf > Folder > Note. Context-manager supported (`__enter__`/`__exit__`/`close`/`__del__`).
- **CLI** (`memorius/cli/main.py`) — `memorius store/search/get/update/delete/list/prune/repair/consolidate/extract/factcheck/context/learn/recall/serve/serve-rest/bookcase/doctor/obsidian/graph/...`.
- **MCP server** (`memorius/mcp_server.py:397 McpServer.run`) — stdio JSON-RPC, ~27 tools (`memorius_*`), one handler per tool (`tool_memorius_*`).
- **REST server** (`memorius/rest_server.py:772 run_rest_server`) — FastAPI on `127.0.0.1:8912` by default, optional API key (`MEMORIUS_API_KEY`), CORS localhost-only, rate limiting, Prometheus metrics, TLS optional.
- **Bookcase** (`cli/main.py:720 cmd_bookcase`) — uvicorn `Server` in a `threading.Thread` serving the REST app on loopback, plus a static-file HTTP thread.
- **Hook engine** (`memorius/hooks/engine.py:79 HookEngine`) — declarative lifecycle actions (mine_dir, diary, command, webhook, consolidate, factcheck, ...) lazily building a `VaultEngine`.

## Findings

Bullets tagged `[observation|risk|gap]`, grouped by the eight analysis areas.

### 1. VaultEngine API surface

- [observation] `store(content, vault="main", shelf="default", folder="default", note="default", metadata=None, ttl_days=None, _vector=None) -> Memory` (`vault.py:211`). Delegates to `StoreModule.store`; `StoreModule.store` (`store_module.py:76`) validates names, writes vector then meta, verifies both stores contain the new row, does best-effort semantic dedup (>0.92 similarity) and graph auto-link. `ttl_days` writes `expires_at` into metadata.
- [observation] `search(query, vault=None, shelf=None, limit=10, expand_graph=False, graph_hops=1, graph_min_weight=0.3, folder=None, note=None, tags=None, rerank=False) -> list[Memory]` (`vault.py:232`). Queries semantic + episodic SearchModules, merges semantic-first then episodic by distance, caps at `ceil(limit*1.5)` when `expand_graph` else `limit`. Tags post-filtered in Python after vector fetch (Chroma `where` cannot test list membership, per docstring).
- [observation] `get_memory(memory_id) -> Memory | None` (`vault.py:361`) — episodic first, then semantic; invalid UUID returns None via `StoreModule.get`.
- [observation] `update_memory(memory_id, content=None, metadata=None) -> Memory | None` (`vault.py:373`) — episodic first then semantic; shallow-merges metadata; re-embeds on content change.
- [observation] `delete(memory_id, vault=None, shelf=None, dry_run=False) -> dict` (`vault.py:440`) — `found`/`deleted`/`memory_id`/path fields; `ValueError` on invalid ID or mismatched vault/shelf scope. CLI `cmd_delete` adds a confirmation prompt (`--yes` skips) (`cli/main.py:1436-1470`).
- [observation] `list_memories(vault=None, shelf=None, limit=None, with_vectors=True, cursor=None) -> dict{"memories", "next_cursor"}` (`vault.py:391`) — cursor pagination over both stores, composite cursor `created_at~id`.
- [observation] Feature methods: `consolidate(vault=None, similarity_threshold=0.80, dry_run=False)` (`vault.py:551`), `extract_memories(conversation, backend="auto", vault="main", shelf="extracted")` (`vault.py:558`), `check_fact(statement, vault=None)` (`vault.py:570`), `get_context(query, vault=None, max_items=5) -> str` (`vault.py:575`), `get_session_profile(session_id, vault="main")` (`vault.py:582`), `learn`/`recall` exposed as `store_learning(...)` / `recall_learnings(...)` / `list_learnings(...)` / `apply_learning(learning_id)` / `get_learning_stats(...)` (`vault.py:819-999`).
- [observation] `prune(threshold=0.1, dry_run=False, archive=True) -> dict` (`vault.py:647`) — stale candidates from `find_stale_memories` (decay score < threshold or past `expires_at` TTL, `temporal.py:123`); soft-archives by default, hard-deletes per-ID via `delete()` when `archive=False`.
- [observation] `repair(vault=None, reindex=False, dry_run=False) -> dict` (`vault.py:684`) — reconciles vector vs meta: orphaned vectors removed, missing vectors re-embedded when `reindex=True`; reports `orphans_found/removed`, `missing_found/reindexed`, `in_sync`, counts.
- [observation] `mine(text, vault="main", shelf="conversations", folder="mined", note="transcript")` (`vault.py:471`) — batch-embeds transcript chunks and stores each as episodic memory.
- [risk] `VaultEngine.__init__` raises directly if `EmbeddingFactory.create` fails; class-level `_consolidation_daemon = None` guard prevents `__del__` AttributeError on half-initialized engines (`vault.py:59-64`).
- [gap] `close()` swallows every exception (`except Exception: pass`, `vault.py:123-129`) and `__del__` calls it, so cleanup failures (unclosed Chroma/SQLite) are silently masked at interpreter shutdown.

### 2. Service layering: engine vs meta_store vs vector_store vs graph

- [observation] Layering: `VaultEngine` (orchestrator) → `StoreModule`/`SearchModule` (coordination) → `ChromaStore`/`SqliteVecStore` (vector) + `SQLiteStore` (meta). `graph.py` is reached only through `SQLiteStore` adapter methods (`init_graph`, `link_memories`, `get_linked`, `expand_graph`, `get_graph_stats`, `get_graph_data`, `meta_store.py:202-235`).
- [observation] Episodic/semantic split: two vector stores (`vectors`, `vectors_episodic`) and two meta stores (`memorius.db` legacy semantic path, `meta_episodic`) created in `VaultEngine.__init__` (`vault.py:84-105`). Routing in `store()` is a path heuristic: episodic only when `shelf=="conversations" AND folder=="mined" AND note=="transcript"` (`vault.py:147-166`, `vault.py:325-336`). All other writes — including `mine` output — go to semantic via `_get_store_module_for_memory`.
- [risk] No cross-store transactions: `StoreModule.store` (`store_module.py:76`) writes vector first, then meta, then verifies; a meta failure after vector success (or vice versa) leaves drift with no rollback. `repair()` is the offline remedy, never run automatically on write paths or startup.
- [risk] Leaky abstraction: `VaultEngine.repair` reaches into `self._vector._lazy_client()` and `client.list_collections()`/`col.get(include=[])` (`vault.py:705-718`) — ChromaDB internals bypassing the `VectorStore` interface. `sqlite_vec_store` has no `list_collections` equivalent, so `repair()` is Chroma-specific despite the abstraction.
- [gap] Duplication: `list_memories` exists on `VaultEngine` (`vault.py:391`), `StoreModule` (`store_module.py:251`), and `SQLiteStore.list_memories_meta` (`meta_store.py:503`); `get_by_ids` exists on `VaultEngine`, `StoreModule`, and both vector stores; `delete` exists on `VaultEngine`, `StoreModule`, `SQLiteStore.delete_memory`, and both vector stores. Callers must pick the right layer or get inconsistent results (e.g. engine-level `delete` checks episodic first then semantic, while `StoreModule.delete` validates scope against the memory's real location).
- [gap] `StoreModule.store` does semantic dedup + graph auto-link (best-effort) on every write — O(N²)-adjacent graph work on the write path, not documented in the engine docstring.

### 3. Auth at service layer (REST/MCP loopback-only)

- [observation] MCP (`memorius/mcp_server.py`) has **zero authentication**: the entire file contains no authN/authZ; any stdio writer can invoke any tool including `memorius_delete`, `memorius_prune`, `memorius_extract`. Transport is stdio (loopback by deployment), but there is no in-protocol gating of destructive tools. Cross-referenced in `docs/rest-api.html` security table only for REST.
- [observation] REST (`rest_server.py:162-183`): `MEMORIUS_API_KEY` env var → `Authorization: Bearer <key>` checked with `hmac.compare_digest`; 401 otherwise. `/health` exempt. Warns if key < 16 chars. `run_rest_server` prints a warning when bound to non-localhost without a key (`rest_server.py:796-806`). Default bind `127.0.0.1:8912` (`rest_server.py:772`).
- [observation] REST CORS: `allow_origins=["app://obsidian.md"]` + `allow_origin_regex` for `127.0.0.1`/`localhost` (`rest_server.py:193-196`). Rate limit 500 req/min/IP, in-memory, resets on restart and is per-worker (`rest_server.py:99-102, 213-234`). Body limit `MAX_CONTENT_LENGTH` (100KB) enforced by middleware (`rest_server.py:203-225`).
- [observation] Hooks engine (`memorius/hooks/engine.py`): `allow_command_hooks` defaults False; command actions use `shlex.split` + `shell=False` (`hooks/engine.py:510-517`). Webhook action blocks private/loopback/link-local/reserved/multicast IPs and metadata hostnames after a single DNS resolve (`hooks/engine.py:543-568`).
- [gap] Webhook SSRF: DNS is resolved once then IPs checked; a DNS-rebind (public → internal after the check) bypasses it, noted in the code comment at `hooks/engine.py:547`. Hostname string match on `metadata.google.internal` is subdomain-bypassable.
- [gap] MCP has no message-size cap on `sys.stdin.readline()` (`mcp_server.py:438`) — OOM risk on huge JSON payloads; REST enforces 100KB but MCP does not.

### 4. Middleware

- [observation] `McpServer.run()` installs a JSON `logging.Formatter` on the `memorius` logger (clears existing handlers, adds `StreamHandler`) — timestamp/level/message/logger, exception info included (`mcp_server.py:399-417`). `rest_server.py:176-190` installs the same JSON formatter.
- [observation] MCP JSON-RPC loop: `consecutive_errors` resets to 0 on successful handling, increments on `JSONDecodeError` and generic `Exception`; shutdown (`break`) when `>= max_consecutive_errors = 10` (`mcp_server.py:435-465`). EOFError / empty stdin breaks the loop cleanly.
- [risk] The counter only tracks *consecutive* errors — interleaving valid and invalid requests resets it, so the 10-error shutdown threshold can be avoided by an interleaving client.
- [gap] CLI `main()` has no top-level exception handler around command dispatch (`cli/main.py:338-345`); unhandled exceptions in handlers (e.g. `cmd_store` reading unbounded stdin, `cmd_search` from stdin) become raw tracebacks. Individual commands guard their own input (e.g. `cmd_delete` confirmation, `cmd_update` JSON parse).

### 5. Error handling: ValueError vs exceptions vs {"error":...} dicts

- [observation] Three error styles coexist:
  - `ValueError` raised by `memorius.validation`: `validate_name` (`validation.py:22`), `validate_memory_id` (UUID check, `validation.py:53`), `validate_session_id` (`validation.py:79`), `validate_content` (`validation.py:114`). Constants: `MAX_NAME_LENGTH=128`, `MAX_SESSION_ID_LENGTH=128`, `MAX_CONTENT_LENGTH=100_000`, `MAX_FIELD_LENGTH=1_000`, `MAX_SEARCH_LIMIT=100`, `MAX_DIARY_CONTENT=50_000`, `VALID_NAME_RE=^[a-zA-Z0-9_\-]+$`, `VALID_SESSION_ID_RE=^[a-zA-Z0-9_\-.]+$`.
  - Exceptions propagated: REST handlers `raise e` / `HTTPException` (`rest_server.py:279-320`); CLI prints errors and returns.
  - `{"error": "..."}` dicts returned directly by MCP tool handlers for validation failures (`mcp_server.py:496-505 store`, `mcp_server.py:520-528 search`, `mcp_server.py:536-543 diary_write`, etc.) — these are **not** JSON-RPC error objects; they are success responses whose `content` text is an error dict, so callers must parse text to detect errors.
- [risk] MCP handlers `tool_memorius_extract` (`args["conversation"]`, `mcp_server.py:634`) and `tool_memorius_factcheck` (`args["statement"]`, `mcp_server.py:646`) index `args` directly → `KeyError` on missing required field → counted as a consecutive MCP error (cap 10) instead of a clean JSON-RPC invalid-params error. `tool_memorius_context` (`args["query"]`, line 660) and `tool_memorius_session_profile` (`args["session_id"]`, line 673) same pattern.
- [observation] MCP name/path validation uses `_validate_name`/`_validate_session_id`/`_validate_memory_id` and converts `ValueError` → `{"error": str(e)}` (e.g. `tool_memorius_delete` lines 743-751). `tool_memorius_prune` (`mcp_server.py:758`) does `float(args.get("threshold", 0.1))` with no try — non-numeric → exception → consecutive error count.
- [risk] `McpServer._handle_call_tool` returns `handler(arguments)` directly; if a handler raises unexpectedly it escapes to `run()`'s generic `except` and counts toward the shutdown cap — no per-tool JSON-RPC error boundary.

### 6. Scaling

- [observation] Single-instance guard for `memorius serve` only (`cli/main.py:354-367`): `acquire_serve_lock(config, reclaim=...)` — exclusive non-blocking `fcntl.flock` on `<storage.path>/serve.lock`, PID stamped; live holder → `ServeAlreadyRunningError`; dead holder → kernel-released flock stolen on retry (`single_instance.py:116-170`). `_reclaim_lock` sends SIGTERM, waits ~3s, then SIGKILL (`single_instance.py:172-192`). No-op with warning on platforms without `fcntl` (Windows). Covered by `tests/test_single_instance.py` and `tests/test_serve_single_instance.py`.
- [gap] `serve-rest --daemon` uses a *separate*, unrelated mechanism: `Popen(start_new_session=True)` writes `proc.pid` to `~/.memorius/serve.pid`; `_stop_daemon` SIGTERMs the PID without verifying it is a memorius process (`cli/main.py:836-868, 877-930`). Two guards, two PID files, no coordination.
- [observation] Cursor pagination: `SQLiteStore.list_memories_meta(..., cursor="timestamp~id")` with `(created_at, id) < (?, ?)` ordering (`meta_store.py:503-562`); `VaultEngine.list_memories` merges episodic + semantic results and re-sorts by `created_at` DESC (`vault.py:391-421`). `SearchModule` search has no cursor; MCP `memorius_search` passes `cursor` straight through to `engine.search` which ignores it (cursor only exists on `list_memories`) — MCP search schema advertises `cursor` but `VaultEngine.search` has no `cursor` parameter (`mcp_server.py:509-529`, `vault.py:232`).
- [observation] TTL/decay: `ARCHIVE_THRESHOLD=0.1` (`temporal.py:24`); `find_stale_memories` flags decay score < threshold or past `expires_at` (`temporal.py:123`); `VaultEngine.prune` archives/hard-deletes stale (`vault.py:647-690`).
- [observation] Consolidation: `ConsolidationDaemon(threading.Thread, daemon=True)` (`consolidation.py:46`) — `run()` waits `interval_seconds` then calls `_run_cycle()`, which is `pass` (no-op) (`consolidation.py:53-62`). The one-shot `consolidate()` does O(N²) greedy cosine clustering over up to 10,000 memories (`consolidation.py:236-330`). `VaultEngine.__init__` starts the daemon only when `consolidation.enabled` (`vault.py:115-122`). Covered by `tests/test_consolidation_daemon.py` (start/stop lifecycle only).
- [observation] Doctor: `doctor.run_checks(engine)` — 6 checks: config keys, storage dir writable, ONNX model present, `memory_meta` row count vs Chroma vector count (drift → "run `memorius repair`"), collection name length ≤ 63, graph edges present when memories > 10 (`doctor.py:40-135`). All best-effort: failures become `warn`/`fail` entries, never raise; `healthy` requires all checks `ok`/`skip`.
- [observation] Repair for drift: `VaultEngine.repair` enumerates all Chroma collections, finds orphaned vector IDs (no `memory_meta` row) and missing IDs (meta row with no vector), removes orphans and re-embeds missing when `reindex=True` (`vault.py:684-786`). Metadata store is source of truth. Dry-run supported.

### 7. Concurrency

- [observation] Bookcase (`cli/main.py:720-814`): uvicorn `uvicorn.Server(uvicorn.Config(app, host="127.0.0.1", port=..., log_level="warning"))` run in `threading.Thread(daemon=True)` (`cli/main.py:767-772`), plus `http.server.ThreadingHTTPServer` static assets in another daemon thread (`cli/main.py:785-790`). Loopback-only (`127.0.0.1`).
- [observation] `serve-rest --daemon`: `subprocess.Popen(..., start_new_session=True, stdin/stdout/stderr=DEVNULL)` on Unix (`cli/main.py:926-928`); detached so it outlives the CLI; parent writes the PID file synchronously from `proc.pid` (`cli/main.py:916-918`).
- [observation] Thread-safety assumptions: `SQLiteStore` uses thread-local connections per db path + one `threading.Lock` per instance + `PRAGMA busy_timeout=5000` + WAL (`meta_store.py:55-70`, `meta_store.py:113-128`). `sqlite_vec_store.SqliteVecStore` uses `threading.local()` connection + one `threading.Lock` (`sqlite_vec_store.py:42-44`, `105`). `ChromaStore` creates a lazy `PersistentClient` per instance with a collection cache dict and `_retry` backoff (`vector_store.py:82-103`, `vector_store.py:55-64`); no explicit lock around collection cache or client creation. Multiple engine instances (e.g. bookcase thread + CLI) opening the same storage dir rely on SQLite WAL + Chroma internal locking, not on the memorius layer.
- [gap] `VaultEngine.close()` nulls `self._vector` etc. without closing Chroma/SQLite resources (`vault.py:123-129`) — relies on `atexit` in `meta_store` (`meta_store.py:41-52`) and process exit; concurrent engine instances share thread-local connection maps keyed by db path.

### 8. Background jobs

- [observation] Consolidation daemon: started in `VaultEngine.__init__` when `config.consolidation.enabled` (`vault.py:115-122`), stopped+joined (timeout 2s) in `close()` (`vault.py:123-126`). `_run_cycle` is empty (`consolidation.py:60`); the daemon does no periodic work today. `tests/test_consolidation_daemon.py` asserts lifecycle (daemon attaches to engine, `stop()`/`join()` detaches it) but does not exercise any consolidation cycle.
- [observation] Doctor checks are on-demand (`memorius doctor`, `GET /doctor`, `McpServer.tool_memorius_doctor`) — `run_checks(engine)` returns a structured report, never scheduled. No background health-check daemon exists.
- [gap] No background job for TTL expiry: `expires_at` metadata is evaluated only inside `find_stale_memories` → `prune`, which is manual (`memorius prune`, `POST /prune`, MCP `memorius_prune` default `dry_run=True`). Nothing archives expired memories automatically.

## Highlights

1. **Two network surfaces with asymmetric security:** MCP (stdio, zero auth, destructive tools exposed) vs REST (API key, rate limiting, CORS localhost-only, body limits). MCP handlers return `{"error":...}` text blobs instead of JSON-RPC errors, and required-arg access via `args[...]` raises `KeyError` that burns the 10-consecutive-error shutdown cap (`mcp_server.py:435-465, 634, 646`).
2. **No cross-store consistency:** vector and meta stores are written non-atomically (`store_module.py:76-96`); drift is only repaired on demand via `VaultEngine.repair`, which reaches into Chroma internals (`vault.py:705-718`). The episodic/semantic split adds a fragile path-based routing heuristic in `store()` (`vault.py:325-336`).
3. **Scaling primitives are partially implemented:** single-instance `flock` guard exists for `memorius serve` only (`single_instance.py:116-170`); `serve-rest --daemon` uses a separate uncoordinated PID file (`cli/main.py:877-930`); cursor pagination works for `list` but `search` advertises an unused `cursor`; the consolidation daemon thread exists but its run cycle is a no-op (`consolidation.py:60`).

## Domain summary

memorius v0.9.3 is a local-first memory vault: a `VaultEngine` orchestrates a vector store (ChromaDB by default, sqlite-vec optional) and a SQLite metadata store over a Vault > Shelf > Folder > Note hierarchy, exposed through a CLI, a stdio MCP server with no authentication, and a FastAPI REST server with optional API-key auth, rate limiting, and CORS restricted to loopback/Obsidian. Temporal decay, a knowledge graph, consolidation, pruning, and doctor health checks sit on top; the single-instance flock guard protects `memorius serve` but not `serve-rest --daemon`, and the consolidation daemon thread currently runs an empty cycle. The clearest place to continue work is `memorius/vault.py` (engine API, drift repair, pruning), `memorius/mcp_server.py` (MCP error handling/auth boundary), and `memorius/single_instance.py` (guard scope). All claims above are backed by line references in those files.
